# Analytics (`services/analytics`)

Component 2 of the toolkit (objectives: the root CLAUDE.md): the techniques (metrics), the recommenders and detectors
(decisions), a Rust core with a Python API (`turbo_parakeet`) and a Java binding. Rust module paths (`common/`,
`techniques/`, `recommenders/`, `bindings/`) are relative to `services/analytics/src/`; other paths are relative to the
repository root. Items in ToDo.md are cited by number.

# Technology
- Arrow columnar data format throughout
- Python with Rust extensions via pyo3, with Arrow at the FFI boundary for performance
- Polars as the primary Python-facing dataframe library; the Rust kernels are moving to native arrow-rs (ToDo 14)

# Analytical Functions

Every technique is used the same way — `Impl(**params).add({"name": frame, ...}).result()` —
and returns one flat table: `df_a, col_a[, df_b, col_b[, df_c, col_c]] | status | descriptors | metrics | conclusions`.
`status` ∈ {computed, ineligible, pruned}; null = not computed, NaN = computed but undefined.
Ineligible columns/pairs are always listed, never dropped. Results must export to native Arrow
(`result().to_arrow()`, checked in every contract test): never a Polars-only dtype such as Int128 —
use Decimal(38, 0) for 128-bit integers. `add()` accepts Polars DataFrames / LazyFrames and any Arrow
tabular object (pyarrow Table, RecordBatch, RecordBatchReader — anything with `__arrow_c_stream__`).
Int128 / UInt128 columns, at any depth, are ineligible in every technique: Arrow has no 128-bit integer
(`turbo_parakeet._dtypes.WIDE_INTEGERS`). Thresholds are keyword-only
constructor arguments with the defaults below. Techniques report metrics only (statistics, estimates,
effect sizes); threshold decisions such as "use REE" belong to the recommenders and detectors. Existing
conclusions, and their threshold keywords, are removed as the recommender or detector that owns each decision
lands (ToDo 13); until then they remain. Describe's `min` / `max` / `unique` / `est_*` count as metrics; its
`class` moves to the recommenders. Techniques are grouped by **scope** —
how column combinations are enumerated.

## 1. Per-column (one column at a time)

**GCD — `turbo_parakeet.techniques.gcd`** (`GcdRust`, `GcdNumpy`, ★`GcdMath`). ClickHouse GCD-codec method: the GCD of the magnitudes of each integer-backed column's raw physical values (Int/UInt 8–64, Decimal → unscaled, Date → days, Datetime/Duration → time unit, Time → ns). Nulls skipped; all-null / all-zero / zero-row → 0; `gcd` is Decimal(38, 0); other dtypes (incl. Categorical/Enum and Int128/UInt128) → ineligible. Descriptor `dtype` (Python `str(dtype)`) on every row. Conclusion `gcd_compressible` = gcd > 1. Rust: rayon-parallel across columns and 64K-value chunks, `binary_gcd(g, v % g)` fold with early exit at 1.

**Describe — `turbo_parakeet.techniques.describe`** (`DescribeRust`, `DescribeDataFusion`, ★`DescribePolars`). Profile for choosing narrower / more compressible Arrow types. Metrics: counts, byte/list lengths, `gcd`, byte totals (`sum_len`, `sum_len_unique`), significant-digit counts, float stats (NaN/inf/fractional, decimal places, f32 round trip), numeric-string and ISO 8601 counts (Rust byte scanners / Rust-regex elsewhere — linear time), Datetime local-midnight count, Arrow IPC sizes (classic layout, plain + ZSTD) and Polars native-layout IPC sizes, and the same for list inner values. Conclusions: `min` / `max` (String, rendered by arrow-rs — `common::text::render_value`; none for List/Array/Struct), `unique`, `est_cardinality` / `est_low` / `est_high` / `est_method` ∈ {observed, hll, schnabel, chao1} by the ratio rule (d distinct of n non-null: d/n ≥ 0.5 → the count, with HLL's ±3σ interval floored at the proven count; else Schnabel (3-way seeded split) → Chao1, floored at the count), `estimates_agree`, and `class` ∈ {null, constant, boolean, ordinal, categorical, discrete} (techniques/single_column/unordered/{cardinality_estimators.rs, describe/conclusions.rs}; turbo_parakeet/techniques/describe/base.py is the reference). Private INPUTS (argmin, argmax, f1, f2, capture history) feed the base's conclusions and never appear in results. Keywords: `categorical_threshold=10_000`, `zstd_level=1`, `seed=0`. Agreement: metrics exact except ZSTD sizes (1%); min/max/unique/class exact; est_cardinality/low/high 10%.

**Top-k — `turbo_parakeet.techniques.top_k`** (`TopKHeavyKeeperRust`, `TopKSpaceSavingRust`, ★`TopKPolars`). Each column's k most frequent non-null values. Metrics `n_non_null`, `top_k` (`List<Struct<value: Utf8, count: UInt64, error: UInt64>>`, count desc then row; values rendered by arrow-rs via `_plugin.render` in the base, from one row per item; non-UTF-8 binary → null) and `sketch_bytes`; conclusion `dominated` = top-1 share ≥ `dominance_threshold=0.5`. `error` = SpaceSaving's over-count bound (true ∈ [count − error, count]), 0 exact, null HeavyKeeper. Keywords `k=5`, `memory_bytes=None` → max(16 KiB, k × 1 KiB) (both sketches sized to fit it; too small for k, or above 4 GiB → ValueError), `seed=0` (HeavyKeeper). Rust: techniques/single_column/unordered/{top_k.rs (shared indexed min-heap `Counters`, `MAX_MEMORY_BYTES`), space_saving.rs (mergeable; 2²⁰-row chunks merged in order, in waves of the thread count; peak ≈ threads × (wave + 2) × budget), heavy_keeper.rs (d = 2, b = 1.08, 32-bit fingerprints, selective increment at count ≤ n_min; no merge)}. Agreement: `n_non_null` exact, precision vs the reference's list ≥ 0.9 (a lower bound under ties), SpaceSaving bounds hold, HeavyKeeper mean relative error ≤ 5%. Benchmark: tests/performance/benchmark_top_k.py (speed, peak memory, tie-aware precision, ARE/AAE, bounds; per stream and k × budget variant; `--rows N` scale run). **Outcome:** both reach precision 1.0 (counts within 0.05%) on Zipf α ≥ 1.1 at the default 16 KiB; at equal memory HeavyKeeper is more accurate on light skew (Zipf 0.8: precision 1.0 vs 0.8 at 4 KiB) and 2–3× faster per row (SpaceSaving wins only one long column, through chunk parallelism); SpaceSaving's bounds always held; neither separates near-tied values unless the budget covers the tail (flat / skewed tails). One-shot, both kernels encode the whole column first (≈ 9 B/row), so their process memory is not smaller than Polars' — the 16 KiB sketch pays off only when fed batch by batch (streaming).

**Distinct count — `turbo_parakeet.techniques.distinct_count`** (`DistinctCountHllRust`, `DistinctCountPolarsApprox`, ★`DistinctCountPolars`). Estimated distinct non-null values per column. Metrics `n_non_null`, `n_distinct` (Float64), `low` / `high` (±3σ, floored at 0, capped at `n_non_null`; null when the sketch exposes no error), `std_error` (relative; 0 exact), `sketch_bytes`; descriptor `dtype`. Floats canonical, Categorical / Enum by string. Eligible: the Rust encoder's scalar dtypes in a non-empty column (nested, Binary, Struct, Null, Object, 128-bit ineligible). Keyword `precision=14` (HLL, 4..=18; `DistinctCountPolarsApprox` accepts and ignores it). Rust: techniques/single_column/unordered/distinct_count.rs (+ hll.rs; 64K-row chunk sketches merged by register max, Ertl's estimator). Agreement: `n_non_null` exact; `n_distinct` RTOL 4·1.04/√2^p (HLL) / 0.05 (PolarsApprox) plus ATOL 2 for register collisions at small d. Benchmark: tests/performance/benchmark_distinct_count.py. **Outcome:** Rust HLL ≈ 2–3× faster than exact Polars `n_unique` but not faster than Polars `approx_n_unique` on long string columns (0.84–0.92×), with higher peak memory (whole column encoded first, ≈ 9 B/row; 349 MB vs ≈ 4 MB at 10M × 4); max error at p = 14 ≈ 1–2%.

**Population cardinality — `turbo_parakeet.techniques.population_cardinality`** (`PopulationCardinalityRust`, ★`PopulationCardinalityPolars`). Distinct values in the population behind a sample, unseen ones included. Metrics `n_non_null`, `n_distinct`, `f1`, `f2` (UInt64) and `chao1` / `schnabel` each with `_low` / `_high` (95%): bias-corrected Chao1 (log-normal interval) and Schnabel over a seeded 3-way row split (Byar's interval); Schnabel is NaN when undefined (d/n ≥ 0.5 or no recapture); Chao1 is degenerate (≈ n²/2) when every value occurs once. Both are always reported: choosing an estimator is the recommenders' job. Eligibility as Distinct count. Keyword `seed=0`. Rust: techniques/single_column/unordered/population_cardinality.rs (Describe's frequency pass + cardinality_estimators.rs); reference: Polars `group_by` + NumPy SplitMix split + describe/estimators.py. Agreement: counts exact, estimates RTOL / ATOL 1e-9. `accuracy(..., truth=)` with a known population D adds `observed_rel_err`, `<est>_rel_err`, `<est>_n_undefined`, `<est>_coverage`. Benchmark: tests/performance/benchmark_population_cardinality.py (datagen.population_samples). **Outcome:** Rust 4–8× total vs the Polars / NumPy reference, agreement ≈ 1e-16; on population samples Chao1 and Schnabel beat the observed count but under-estimate heavily under-sampled Zipf populations.

**Marginal entropy — `turbo_parakeet.techniques.marginal_entropy`** (`MarginalEntropyRust`, `MarginalEntropyAmsRust`, ★`MarginalEntropyPolars`). Shannon entropy of each column in bits, null one category (the joint entropies' policy). Metrics `h`, `n_rows` (counts nulls). Eligible: any Rust-encodable dtype in a non-empty frame. Keywords (AMS only) `num_samples=4096`, `seed=0`. Rust: techniques/single_column/unordered/{marginal_entropy.rs, ams_entropy.rs}. Agreement: exact RTOL 1e-9 / ATOL 1e-12; AMS within max(5% of the exact value, 0.1 bits) — the sketch's error is roughly constant in bits (sd ≈ 0.022 bits for a 1-bit column at 4 096 samples), so a relative-only bound fails 1-bit columns about one seed in seven. Benchmark: tests/performance/benchmark_marginal_entropy.py (the pairwise-entropy shapes). **Outcome:** exact Rust 5–9× total vs Polars; AMS is slower than exact Rust everywhere and wins memory only on near-unique data (96 vs 381 MB).

**OneShotRecommender — `turbo_parakeet.recommenders.OneShotRecommender`** (Rust only; not on the uniform contract). Narrowest value-preserving Arrow type per column of one frame. `add(frame)` once (DataFrame, LazyFrame — collected — or any Arrow tabular object; a second `add` raises ValueError) collects exact Describe statistics and sizes (`recommenders::engine::prepare`); `result()` (any number of times, cached) applies step 1 type rules (null → boolean → uint → int → decimal → float → date → time → timestamp → timestamp_with_offset → string; lists → scalar when every list holds one item) and step 2 dictionary encoding for strings (key width from `est_high`, Polars key one code narrower). Candidates carry a predicted IPC size and are tried smallest projected population size first (ties: hierarchy rank); each is cast, verified row by row and measured (Arrow and Polars layouts, plain and ZSTD); the original type is always the last resort. Dictionary candidates are cast with frequency-ordered keys (most frequent value → key 0), and `top_k` / `inner_top_k` (Arrow `Map<Utf8, UInt64>`, before the recommendation columns; null unless the level's `string→dictionary` candidate was not rejected) list the level's values by count, ties to the first seen, at most `top_k` entries (`None`: all; 0: off). Dictionaries are measured with every value in frequency order; pass `top_k=None` to receive the full order the sizes assume. Rankings come from Describe's existing frequency map (`frequencies(.., rank_up_to)` → `Profile.ranking`); `turbo_parakeet.recommenders.to_arrow` turns a result's Polars lists back into maps. Frequency order pays off with UInt16 keys (benchmark: +1.8% ZSTD at 500 values, +8% at 5 000; ≈ 0 with UInt8 keys). Output: the streaming recommender's columns without `first_row`, `n_sampled_rows`, `n_sampled_blocks` (one definition: `recommenders::schema::recommender_fields`); `dtype` is the pyarrow name and names the Arrow type received (e.g. string_view from a Polars frame, large_string from a pyarrow table); `candidates` lists rule, evidence, predicted/projected size and outcome for every candidate. Recommendation columns, in order: `nullable, lossy_formatting, datafusion_type, datafusion_size_bytes, datafusion_size_zstd_bytes, datafusion_size_lz4_bytes, datafusion_ipc_compression, datafusion_ipc_zstd_level, datafusion_ipc_size_bytes, polars_type, polars_size_bytes, polars_size_zstd_bytes, polars_size_lz4_bytes, polars_ipc_compression, polars_ipc_zstd_level, polars_ipc_size_bytes, candidates` (`*_ipc_compression` ∈ `LZ4_FRAME` / `ZSTD`), then the ClickHouse block `clickhouse_type` (Nullable / LowCardinality / Date vs Date32 / DateTime vs DateTime64 / Enum8/16 / FixedString / Time64 / Array / Tuple), `clickhouse_codecs` (e.g. "GCD, ZSTD(3)"), `clickhouse_size_bytes` (predicted by the on-disk emulator `common/clickhouse_sizes.rs`), `clickhouse_candidates` (codec chain, predicted bytes, outcome chosen / rejected / pruned, evidence); then `clickhouse_skip_index` (the DDL fragment, e.g. "set(125) GRANULARITY 1"; null when none) and `clickhouse_skip_indexes` (every candidate: kind, granularity, max_size, fpr, bytes, skip_rows, skip_values, expected_skip_rows, outcome, evidence) — see **Skip-index recommendation** below (the `rec_` prefix is gone). Compression decisions (`recommenders/engine/{clickhouse,compression}.rs`): analytic pruning first — the transform families are none / GCD / Delta / DoubleDelta: GCD is a candidate only if dividing frees a byte at the maximum magnitude (byte-width rule); Delta survives iff the mean delta bytes < the mean value bytes, DoubleDelta iff the mean double-delta bytes < min(value, delta) (statistics from the emulator's integer streams, `stream_delta_stats` in recommenders/engine/column.rs; streaming: the sampled blocks); and the near-incompressible shortcut rules ZSTD out when 1 − H_b/8 < `zstd_min_saving` and the column is mostly distinct — then the emulator measures the survivors (ZSTD level: the lowest within `zstd_level_tolerance` of the best); the winner is the smallest family pick that saves at least `transform_min_saving` over the plain pick (examples, 200K rows: regular DateTime64(3) timestamps → "DoubleDelta, LZ4" 1 971 B against 374 072 B for plain ZSTD(1); a random walk → "Delta, ZSTD(9)"; random Int64 → both pruned). The emulator models Delta / DoubleDelta and two-codec chains (ClickHouse's CompressionCodecMultiple headers; GCD writes its [width, 0] + GCD-value header); Arrow IPC LZ4_FRAME sizes come from liblz4 (`lz4` crate; `common/ipc_sizes.rs`, byte-exact against pyarrow). **Calibration** (`tests/performance/calibrate_clickhouse_sizes.py`, 456 cells against ClickHouse 26.8 via chbench): the GCD (32), Delta (36) and DoubleDelta (30) cells are byte-exact (the on-disk layout was verified by tests/performance/spike_clickhouse_delta.py, byte-exact on 176 cells: 16 columns × 11 chains, widths 1 / 2 / 4 / 8; GCD's old 1.86% was a header fix), other fixed-width types are within max(2% × measured, 256 bytes), `LowCardinality(String)` within 2.5%, String has no tolerance yet (LZ4 median +19%, small ZSTD(1) columns under-predicted up to 78%: ToDo 9); six near-constant Int32 / Bool columns are still over-predicted on LZ4 (925 vs 46 B), the known sparse-serialization gap (ToDo 9). **Skip-index recommendation** (`recommenders/engine/{skip_index.rs, skip_choice.rs}`; point queries `col = v` only, range queries are ToDo 10). At most one ClickHouse skip index per column: `minmax`, `set(N)` (N in `set_max_sizes`) or `bloom_filter(fpr)` (fpr in `bloom_fprs`; a fallback only when no minmax / set passes, and only if skip × column bytes > index bytes), at GRANULARITY G in `skip_granularities`. Metrics come from the existing minmax / set techniques on a population built from the recommended array (observed in the stored order, `expected_skip_rows` under random order); index sizes from the emulator (`common/clickhouse_sizes.rs` `skip_index_bytes`; bloom sized by distinct values per block: ceil(D × b / 8) bytes plus a 1–3-byte header, b = 15 / 10 / 8 / 7 bits for fpr 0.001 / 0.01 / 0.025 / 0.05, as measured in the bench's FINDINGS §10). Decisions: a candidate passes if `skip_rows ≥ min_skip` and `skip_rows − expected_skip_rows ≥ min_gain`; a set is pruned when `overflow_fraction ≥ max_overflow` (high local cardinality); within a kind the coarsest G within 0.02 of the best; across kinds the highest `skip_rows`, ties within 0.02 to the smaller index. Keywords (both recommenders; Python, Rust API, C ABI, Java): `skip_granularities=(1, 2, 4, 8)`, `set_max_sizes=(125, 250)`, `bloom_fprs=(0.025,)`, `min_skip=0.3`, `min_gain=0.1`, `max_overflow=0.1`. Dictionary arrays are decoded before the Polars import in `skip_choice` (they leaked into Polars' process-global categorical mapping and made Categorical sizes flaky). **Calibration** (`tests/performance/calibrate_skip_indexes.py`, 40 chbench suites): minmax / set skip shares and index bytes exact; bloom skip within ~1–2 marks per query (expectation × (1 − fpr)), bloom bytes within 1%. **Handoff:** `turbo_parakeet.recommenders.to_chbench(result, frame, out_dir, columns=None)` (Python only) writes per computed column `<name>.arrow` (original column, normalised to types chbench parses), a chbench suite `<name>.yaml` (chbench's `dataset: {path, column}` form; the recommended vs original type, codec (the recommended transform — GCD / Delta / DoubleDelta — is the codec axis value) and compression axes use chbench's type vocabulary; the skip axis is `["<index>:<G>", "none"]` (chbench's `<index>[:<G>]` grammar) with point queries at 0.001 / 0.01 / 0.05) and `<name>.predicted.json` (predicted bytes per `type|codec|compression` cell), and returns the skipped columns with reasons; its original-type cells use the private bindings `_plugin.clickhouse_profile` / `ipc_body_sizes`. Profile columns after `n_midnight` (both recommenders): `entropy, entropy_low, entropy_high, entropy_method` — Shannon bits of the top-level values, null one category; one-shot is always `exact`, from Describe's frequency pass, which also yields the first rows (`describe/frequencies.rs`) (exact up to float rounding: the counts are reduced in parallel, so `entropy` / `entropy_low` / `entropy_high` can differ in the last bits between runs of the same build — compare them with a tolerance, never bit-for-bit) — and `exemplar_row, exemplar_id, exemplar_value, null_exemplar_row, null_exemplar_id`: the first-seen non-null / null rows (null where none), `exemplar_value` the arrow-rs display text of any type; the `*_id` columns are Null-typed unless `id_columns=[...]` is given, then Structs of those columns with their original types. Int128/UInt128, Object, Null and nested-Null columns ineligible. Keywords: `categorical_threshold=10_000`, `zstd_level=1`, `seed=0`, `top_k=256`, `boolean_pairs=(("true", "false"),)`, `id_columns=None`, and (both recommenders; Python, Rust API, C ABI, Java) `zstd_levels=(1, 3, 9)`, `zstd_level_tolerance=0.01`, `zstd_min_saving=0.10`, `transform_min_saving=0.01`. Oracles are pyarrow/Polars casts and predicted = measured; the streaming recommender is tested for parity against it.

**Streaming Recommend — `turbo_parakeet.recommenders.StreamingRecommender`** (Rust only; not on the uniform contract). OneShotRecommender's dtype recommendations from batches added over time. `add(frame)` any number of times (columns may appear, disappear or start as Null; other type changes raise; each Arrow batch is atomic, one multi-batch `add` is not), `result()` at any point → one row per column: `column, status, dtype, first_row, n_rows, n_null`, Describe's value block (`n_unique, unique, est_*, class, min, max`, lengths, `gcd`, float / numeric-string / ISO counts), the `inner_*` block (list inner values), `n_midnight`, `entropy*` and exemplar columns (as one-shot; the first rows cost O(1) state per column plus one-row id slices), the size columns, `top_k, inner_top_k`, Recommend's columns (`nullable` … `clickhouse_candidates`), `n_sampled_rows, n_sampled_blocks`. Exact running statistics (recommenders/streaming/partial.rs) prove each recommendation on every row (`prove`, `lossy_by_stats` in recommenders/engine/); a seeded Algorithm-L sample of contiguous row blocks (recommenders/streaming/reservoir.rs; compact `copy_rows` pieces) gives ZSTD sizes — those of an IPC file written in `block_rows` batches — and cross-checks the chosen type. Original sizes analytic except Struct / deeper nesting (per-batch sums). Every dtype is distinct-counted (per-column absorb in parallel) by HyperLogLog (techniques/single_column/unordered/hll.rs, p = 14, Ertl's estimator) and a bottom-k distinct sample (recommenders/streaming/distinct_sample.rs, k = max(`categorical_threshold`, 1000)): exact while the sample holds every value, then `n_unique` is floored at k + 1 and the estimate is Schnabel → Chao1 from the sample (`seen` = k + 1), or HLL when d/n ≥ 0.5 — the same rule as Describe; the count is capped at the non-null values (every sampled value seen once → all of them). While exact, the sample also holds each value's full count, first row and (text levels) text, giving the same ranking as one-shot. Memory per eligible level, every dtype: ≈ 16 KB of HLL + a sample of up to ≈ 65 bytes × k (≈ 0.65 MB at k = 10 000), e.g. ≈ 0.65 GB for 1 000 high-cardinality columns; text levels also keep their distinct values' text while exact (k × mean value length). Entropy is `exact` while the sample is exact; past that it is an estimate with a ±3σ interval (`entropy_method` `sample`: from the bottom-k sample, or `ams`: a Chakrabarti–Cormode–McGregor AMS sketch per eligible column, ≈ 4 096 estimators, fed every row). `entropy_estimator="ams"` is the default: `sample` reaches 9.6% error on Zipf 0.8 / 1.1 where `ams` stays ≤ 0.8% on every shape, but `ams` makes `add()` ≈ 2.5–3× slower on a single column and ≈ 6× on a 101-column frame of 50K rows, with ≈ 120 MB more peak memory, and each `add` also holds one 8-byte key per row per column until its batch is absorbed (≈ 8 MB per column per million-row batch: use smaller batches for wide frames); `"sample"` (bottom-k distinct sample with the HyperLogLog distinct count) costs nothing extra but is weak on skewed columns. Extremes for every scalar dtype incl. text / boolean / binary (Categorical by string, Enum by category code). Int128/UInt128, Object and nested-Null columns ineligible (marked by the Python wrapper, `n_null` null). Keywords: `reservoir_rows=524_288` (0: no sample, ZSTD null), `block_rows=65_536`, `categorical_threshold=10_000`, `zstd_level=1`, `seed=0`, `top_k=256`, `boolean_pairs`, `id_columns=None`, `entropy_estimator="ams"`, `zstd_levels`, `zstd_level_tolerance`, `zstd_min_saving`, `transform_min_saving` (as one-shot). **Compression, streaming:** Arrow IPC LZ4 / level sizes are measured on the reservoir sample concatenated, the ClickHouse emulator per sampled block, both scaled by `n_rows / sampled_rows`; GCD and range come from the running statistics, rescaled to the recommended unit; text-derived temporal types map to the wide type (Date32 / DateTime64) and text-derived numerics get no GCD; `reservoir_rows=0` leaves sizes and `clickhouse_codecs` null (`clickhouse_type` is still given). **Skip indexes, streaming:** the sampled reservoir blocks are the window segments (`over_segments`; population and baselines come from the sample, running-count injection is a refinement — ToDo 10), every G whose window exceeds `block_rows` is pruned, and index bytes are scaled by `n_rows / sampled_rows`; same keywords and decisions as one-shot. Parity with one-shot is exact for one batch of fixed-width types with `block_rows` a multiple of 8 192, else within about 2%.

## 1b. Per-column, order-dependent (row order within one column matters)

Same contract and `per_column` scope; implementations read rows in the frame's own order. Rust kernels live in `techniques/single_column/ordered/`.

**Runs test — `turbo_parakeet.techniques.runs_test`** (`RunsTestRust`, ★`RunsTestPolars`). k-category one-sample runs test (Barton & David's generalisation of Wald–Wolfowitz): candidates for Arrow run-end encoding. Metrics `n_rows`, `n_runs` (R = maximal runs of equal consecutive values = REE run-ends length; null one value, floats canonical), `expected_runs` E[R] = 1 + (n² − Σnᵢ²)/n, `z` with Var[R] = [S₂(S₂ + n(n+1)) − 2nS₃ − n³]/(n²(n−1)), `p_value` **one-sided, lower tail** Φ(z) (fewer runs than chance; normal approximation, no continuity correction), `mean_run_length` n/R — the effect size (p vanishes at large n). Var = 0 (n = 1, constant, all distinct) → z, p NaN. No conclusions (REE decisions belong to the recommenders); no keywords. Ineligible: List/Array/Struct/Null/Object, Int128/UInt128, zero-row columns. Rust: techniques/single_column/ordered/runs_test.rs — native neighbour comparison, one hash update per run, 2¹⁶-row chunks merged in row order (rayon), variance numerator exact in i128 up to ≈ 3·10⁹ rows (then f64), R − E exact, Φ via `libm::erfc` (statrs' CDF is only ~1e-10 accurate). Reference: Polars `ne_missing` + `group_by`, exact Python-int moments, `math.erfc`. Agreement: counts exact, floats RTOL 1e-9. Tests also cross-check z with statsmodels' binary `Runs` (optional dependency) and the moments by permutation Monte Carlo. **Outcome:** Rust agrees with the reference on every benchmark; total speedup 16.9x on the former large_dataset.arrow, 3.9x wide 1M x 100, 3.0x long runs 10M x 4 (algorithmic 1.3x: the per-row scan, not hashing, dominates), 1.2x random 10M x 4 (algorithmic 0.7x: one hash insert per row, and each column's counts merge on one thread at the top of the reduce).

**Delta — `turbo_parakeet.techniques.delta`** (`DeltaRust`, ★`DeltaPolars`). How well ClickHouse's Delta / DoubleDelta codecs suit an integer-backed column in its row order. Eligible as GCD (raw physical integers; Decimal → unscaled, Date → days, Datetime / Duration → time unit, Time → ns); floats (Gorilla is out of scope), Boolean, text, Categorical, nested, 128-bit and zero-row columns ineligible. Deltas Δᵢ = xᵢ₊₁ − xᵢ of consecutive non-null values (the delta spans nulls) and double deltas ΔΔᵢ = Δᵢ₊₁ − Δᵢ are exact (128-bit, no wrapping). Metrics: `n_rows, n_non_null, n_deltas`, `delta_min/max`, `double_delta_min/max` (Decimal(38, 0)), `value_bytes_mean`, `delta_bytes_mean`, `double_delta_bytes_mean` (means of sig(v) = bytes of the signed two's-complement form with trailing sign bytes dropped, 0 for v = 0, 0..9), `zero_delta_fraction`, `zero_double_delta_fraction`, `delta_entropy`, `double_delta_entropy` (bits; exactly 0 for a single distinct key), and `expected_delta_bytes_mean`, the exact baseline for a random row order (mean sig over all ordered position pairs; observed − expected = gain from the order). No conclusions, no keywords (whether a codec pays off belongs to the recommenders). Rust: techniques/single_column/ordered/delta.rs. Agreement: counts, ranges, byte means, fractions and baseline exact; entropies RTOL 1e-9. **Outcome:** DeltaRust vs DeltaPolars (Python-int reference, shapes reduced because it is slow; tests/performance/benchmark_delta.py): large_dataset 50K x 101 129.7x algorithmic / 3.3x parallel / 431.5x total; timestamps 1M x 4 152.3x / 3.1x / 474.5x; wide 20K x 100 53.0x / 3.3x / 172.6x.

**MinMax index — `turbo_parakeet.techniques.minmax_index`** (`MinMaxIndexRust`, ★`MinMaxIndexPolars`) and **Set index — `turbo_parakeet.techniques.set_index`** (`SetIndexRust`, ★`SetIndexPolars`). How well a column, in its row order, suits ClickHouse's `minmax` / `set(max_size)` skip indexes. A window of w = `index_granularity × granularity` rows slides one row at a time (every granule alignment; a column shorter than w is one window); per window, the share of point queries `col = v` it lets skip — v by row frequency (`skip_rows_mean/std`) or uniform over distinct values (`skip_values_mean/std`), mean and population std over windows — and `expected_skip_rows/values` under a uniformly random row order (closed form from the counts: hypergeometric `avoid(m)` = C(n − m, w)/C(n, w)): observed − expected = gain from ordering. Both: `n_rows, n_non_null, n_distinct, window_rows, n_windows`. minmax: skipped iff v outside [min, max] of the window's non-null values (all-null window: always); order natural, strings bytewise, Categorical by string, Enum by category order, floats canonical with NaN last; baseline exact. set: entries = distinct values + NULL; > `max_size` (0 = unlimited) → stored empty, skips nothing; also `window_distinct_mean/max`, `overflow_fraction`, `expected_window_distinct` (exact), `expected_overflow_fraction`; baseline exact when unlimited, else a normal approximation with exact mean / variance / conditional means over count classes (O(C²) ≤ O(2n); ≤ 0.01 from Monte Carlo). No conclusions. Keywords `index_granularity=8192`, `granularity=1`, set `max_size=100`. Ineligible: as the runs test (`_dtypes.ORDERED_SCALARS`). Rust: techniques/single_column/ordered/skip_index/{mod.rs (`Population` = dense rank ids + counts; `WindowSums` = exact u128 Σa, Σa², merged by addition — the streaming hook: results = merge(scan(population, segment)) + baseline; `avoid`), minmax.rs (monotonic deques), set.rs (per-id window counts)}; ranges of max(2¹⁶, 4w[, d]) window starts in parallel. References: rolling min/max (minmax); occurrence intervals + difference array (set). Agreement: counts exact, observed RTOL 1e-9 (ATOL 1e-12), baselines 1e-6; plus a brute-force oracle fuzz (tests/skip_index_helpers.py). Recommender use: the skip-index recommendation (streaming: the reservoir blocks as segments).

## 2. Multi-set (distinct-value sets; pairs may span frames)

Pairs are compared only within one **value family** (ints ≤64-bit; String/Categorical/Enum; otherwise exact dtype) — other pairs are ineligible.

**Membership — `turbo_parakeet.techniques.membership`** (`BloomRust`, `BloomFastbloom`, ★`MembershipExact`). Directional containment of distinct values: `ratio_a_in_b`, `ratio_b_in_a`, plus exact distinct/non-null counts. Conclusions (`containment_threshold=0.95`): `unique_a/b`, `relationship` ∈ {pk_pk, fk_pk, pk_fk, mutual, a_in_b, b_in_a, none}. PK-PK needs reciprocal containment of unique values. Bloom implementations: `fp_rate=0.01`; no false negatives.

**Similarity — `turbo_parakeet.techniques.similarity`** (`MinHashRust`, `MinHashDatasketch`, ★`SimilarityExactLRU`). Jaccard `|A∩B|/|A∪B|` and Overlap Coefficient `|A∩B|/min(|A|,|B|)`; conclusions `passes_jaccard` (0.6) / `passes_overlap` (0.95). MinHash implementations prune with LSH (`num_perm=128`, status `pruned`) and verify candidates exactly; the exact reference checks every pair through a per-instance LRU cache of distinct-value sets (`cache_size=4096`) — the comparison being tested is Rust probabilistic pruning vs LRU-cached brute force.

## 3. Ordered (row i of A vs row i of B; within one frame; zero-row frames ineligible)

**Chi-squared — `turbo_parakeet.techniques.chi_squared`** (`ChiSquaredRust`, ★`ChiSquaredScipy`, `ChiSquaredPolarsDS`). Independence test on Boolean/String/Categorical/Enum/integer columns with ≤ `max_unique=1000` values; null rows dropped (`n_valid`). χ² detects any association but not causality; at 50K rows p-values are vanishingly small, so **Cramér's V is the diagnostic**: `associated` = V ≥ 0.3. `low_expected_count` flags unreliable tables.

**Joint entropy — `turbo_parakeet.techniques.pairwise_entropy`** (`PairwiseEntropyRust`, `PairwiseEntropyAmsRust`, ★`PairwiseEntropyPolars`) and **`turbo_parakeet.techniques.threeway_entropy`** (`ThreewayEntropyRust`, `ThreewayEntropyAmsRust`, ★`ThreewayEntropyPolars`). Null is its own category. Pairwise reports `h_a, h_b, h_ab`, `mi = h_a + h_b − h_ab`, `nmi = mi / min(h_a, h_b)`; `redundant` = NMI ≥ 0.9 (one column predicts the other). `near_unique` = joint entropy ≥ log₂(n_rows) − 0.1 (near-unique combinations — a different diagnostic). Threeway reports `h_abc` and `near_unique`. The `*AmsRust` implementations estimate every entropy with a Chakrabarti–Cormode–McGregor AMS-sampling sketch (techniques/single_column/unordered/ams_entropy.rs, pairwise/ordered/ams_joint_entropy.rs): one pass, O(`num_samples`) memory per column / combination whatever the cardinality, a backup sample plus 256 Misra–Gries counters for a dominant item, and two geometric label clocks (row-indexed; indexed by rows of other keys) so per-row work is O(1) amortised even on near-constant streams. Seeds derive from the user seed and the column names (columns put in a canonical name-hash order), so an estimate depends neither on thread scheduling, column order nor the other combinations requested; deterministic for a given build only (string keys come from foldhash, so a foldhash upgrade re-rolls estimates). Keywords `num_samples=4096` (≤ 2²⁰), `seed=0`. Agreement: entropies within max(5%, 0.1 bits) (the sketch's error is roughly constant in bits, so 5% alone fails 1-bit columns); MI within 5%·(h_a + h_b + h_ab) + 0.3 bits, NMI within that ÷ min(h_a, h_b); `n_rows` exact; conclusions not compared. **Outcome:** max relative error 0.3–4.3%, MI error up to 0.14 bits; one-shot, AMS is slower than `*Rust` everywhere except near-unique 1M-row data (on par) — ~330× slower on many small combinations (fixed ≈ c·ln m events per sketch) — and its memory win is on high-cardinality data only (125 vs 579 MB, pairwise near-unique 1M × 9). Use the exact kernels one-shot; the sketch is for streaming. Benchmarks: the two entropy benchmarks (speed, peak memory, error against the reference and the exact Rust kernel; near-unique 1M x 9, near-constant 1M x 3).

**Adjusted Rand Index — `turbo_parakeet.techniques.adjusted_rand`** (`AdjustedRandRust`, ★`AdjustedRandSklearn`). Chance-corrected partition agreement (1 = identical, ≈0 = chance, floor −0.5); null rows dropped (`n_valid`); `same_partition` = ARI ≥ 0.9. Unlike NMI it is chance-adjusted; unlike χ² it measures partition identity.

★ = accuracy reference.

**Not implemented:** run-length / REE compression analysis (`run_length.py` was deleted in `93f6dcb`). The runs test (section 1b) covers run structure as a technique; REE is never recommended: DataFusion 54 and 55 reject MIN / MAX over REE columns (`tests/performance/spike_datafusion_ree.py` re-checks after an upgrade).

# Testing Convention
Every technique package declares `REFERENCE` (the exact accuracy reference) and `IMPLEMENTATIONS`.
- `tests/test_<technique>.py` — **accuracy only**, never timed. Same four blocks everywhere, via `tests/harness.py`:
  1. contract (every implementation): schema, every combination in canonical order, non-computed rows null;
  2. reference agreement (every non-reference implementation): `impl.agreement(result, reference_result)` —
     exact implementations within the technique's `RTOL/ATOL`; Bloom: no false negatives + aggregate FP ≤ 3×fp_rate;
     MinHash: evaluated pairs exact + recall ≥ 0.85;
  3. known answers (hand-worked cases, reference included);
  4. conclusions, once per technique base, via `with_metrics` (including a NaN row).
  Large-frame agreement / parity tests run on `datagen.large_dataset()` and `large_dataset_mixed()` (nulls, runs, sorted groups).
  Optional libraries missing → visible skip naming the library.
- `tests/performance/benchmark_<technique>.py` — **speed, peak memory and accuracy**: ~20-line scripts calling
  `harness.run(package, datasets[, variants])` on `datagen.large_dataset()` (50K × 101, generated) + a narrow/long + a wide shape
  (a `Dataset.truth` — known population values — reaches `accuracy(..., truth=...)`, e.g. population cardinality).
  One child process per (dataset, implementation, variant, threads) — one result row each — reading the dataset from Arrow IPC
  written once: the warm-up `Impl(**params).add(frames).result()` gives `peak_mb` (working set above the loaded data;
  `peak_is_upper_bound`: true when the warm-up never exceeded the load-time peak, so `peak_mb` only bounds the figure from above),
  then 5 timed runs (fresh instance) give median/min. Rust implementations run at N and 1 threads
  (`RAYON_NUM_THREADS=1`, `POLARS_MAX_THREADS=1`): **algorithmic** (fastest non-Rust ÷ Rust@1), **parallel** (Rust@1 ÷ Rust@N),
  **total**. Every result is scored against the reference — `agrees` (`agreement()`) and `Technique.accuracy()` (default: max / p95
  relative error over `ACCURACY_METRICS` and `n_missing`; Top-k: tie-aware precision, ARE / AAE, bound violations against exact
  counts) — and an estimator's (`EXACT = False`) also against its exact Rust sibling (`exact_rust_*`, `speedup_vs_exact_rust`).
  `Variant.estimator_params` (e.g. `memory_bytes`) go to estimators only. Never a gate. Results →
  `tests/performance/results/<technique>_<timestamp>.arrow` (Arrow IPC, ZSTD; git-ignored).
- Rust unit tests: `cargo test --lib <module>::` from `services/analytics/` with `PYO3_PYTHON` set to the env's `python.exe` and the env dir on `PATH` (else `STATUS_DLL_NOT_FOUND`).

# Entropy dense re-encoding (common/encode.rs + techniques/pairwise/ordered/joint_entropy.rs)
Columns feeding `pairwise_joint_entropy`/`threeway_joint_entropy` are dictionary-encoded to dense ids `0..card` via `densify`/`build_dense_cache_par` (nulls become their own id, so the per-row loop carries no separate null mask). Joint keys are then combined arithmetically (`(a·Kb + b)·Kc + c`) instead of hashing multi-field tuples:
- joint space ≤ 2²⁰ → flat-array counting, no hashing (thread-local scratch array + touched-slot list for O(distinct) reset)
- joint space > 2²⁰ but ≤ u64::MAX → single-u64 hash map
- joint space > u64::MAX (only reachable past ~2.6M rows) → u128-packed hash map fallback

This encoding is entropy/chi²-only — it's value-relabeling and has no cross-column/cross-frame identity, which is fine since entropy is invariant under injective relabeling. Bloom/MinHash must keep using the value-stable `encode_series`/`build_column_cache_par` path since they compare actual values across columns and frames.

# Cross-cutting notes (not bugs, worth documenting)
- `encode_series` returns `EncodedColumn { values, is_null }` — nulls are out-of-band (no in-band sentinel), floats are canonicalised (`-0.0`→`0.0`, all NaN payloads→one key). Null policy per module: entropy = null is a category; chi² = null rows dropped; minhash/bloom = nulls skipped. Keep this in mind when deriving MI from entropy + chi² outputs. Entropy additionally densifies `EncodedColumn` → `DenseColumn` (`0..card` ids) via `densify` — see "Entropy dense re-encoding" above.
- `String / categorical / enum / list / decimal types route through foldhash → u64` (categorical/enum are cast to their string value first, so a categorical `"x"` hashes identically to the string `"x"` and identically across frames regardless of physical code). Collision probability at 50K rows is ~6×10⁻¹¹ per pair — negligible for entropy/χ², irrelevant for MinHash (deterministic seed across columns). foldhash `FixedState` is NOT stable across crate versions/platforms — don't persist bloom bit arrays or minhash signatures across rebuilds for hashed dtypes.
- chi² and ARI share `build_contingency` (techniques/pairwise/ordered/contingency.rs): dense-id counting, drop-null policy, marginals + non-zero cells. Entropy keeps its own counting (null-as-category — different policy by design).
